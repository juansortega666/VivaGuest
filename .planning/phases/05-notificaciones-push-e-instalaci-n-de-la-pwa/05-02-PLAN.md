el destino soporta el formato declarativo, y la unica superficie por la que el admin sabe quien
quedo sin avisos.

dispositivo y no de la persona, y §5.2 y §8.6 quedan implementadas tal como estan escritas.

columna** y la evidencia solo la mueven funciones `security definer`.

**Las ocho reglas del patron de funcion, literales de la migracion 09 y repetidas en la 15:**

  1. `language plpgsql security definer set search_path = ''`.
  2. Todo nombre calificado por esquema, `auth.uid()` incluido.
  3. Al lado de CADA definicion, sin excepcion:
       `revoke all on function public.<f>(<args>) from public, anon;`
       `grant execute on function public.<f>(<args>) to authenticated;`
     No se hereda. Medido dos veces en PG 17.6: `alter default privileges` no puede quitarle
     `EXECUTE` a PUBLIC porque Postgres refusiona `acldefault('f', owner)`, que siempre trae `=X`.
  4. Guarda de rol con `private.is_admin()`, que consulta `profiles` y nunca un claim del JWT.
  5. `select ... for update` sobre la fila objetivo antes de escribirla.
  6. `42501` cuando el problema es de permiso o cuando distinguir el caso seria un oraculo de
     enumeracion; `P0001` con `hint` en espanol cuando el usuario si esta autorizado y falla el
     estado. `mapDbError()` lee el **`hint`** en `P0001`, no el `message`.
  7. `public.today_bog()` y nunca `current_date`.
  8. Nada de insertar a mano en tablas de bitacora que ya tienen trigger.

**El enum `notification_type` NO SE TOCA.** Once valores, decision fijada en el plan 03-03 y
repetida en `05-CONTEXT.md`. Este plan crea un enum **nuevo y distinto**
(`public.grado_verificacion_aviso`), que no colisiona con nada.

**Por que el admin no recibe `select` sobre `push_subscriptions`:** el `endpoint` es una
**credencial portadora**. Quien lo tiene puede enviarle avisos a ese telefono. El admin no necesita
ninguno de los tres campos de credencial para cumplir D-03; necesita un agregado. La policy
`push_subs_own_all` se queda tal cual y **no se anade ninguna policy de admin**.

**La forma exacta de los tres estados de `05-UI-SPEC.md` §5.2, que este schema tiene que poder
derivar:**

| Estado | Derivacion |
|---|---|
| `Activos` | >= 1 suscripcion con `revoked_at is null` **y** verificacion confirmada **por toque** |
| `Sin probar` | suscripcion viva, pero la prueba nunca se confirmo, o se confirmo a mano |
| `Sin avisos` | cero suscripciones vivas |

**(a) El enum nuevo.** `create type public.grado_verificacion_aviso as enum ('toque', 'manual');`
Con `comment on type` que diga la asimetria: `toque` es evidencia de que el aviso se pinto en la
pantalla y era tocable; `manual` es la palabra de quien acompana el onboarding. `toque` puede
reemplazar a `manual`; al reves nunca.

**(b) Las siete columnas de `push_subscriptions`, todas aditivas:**

| Columna | Tipo | Por que |
|---|---|---|
| `soporta_declarativo` | `boolean not null default false` | D-07. Lo escribe el cliente al suscribirse, por feature detect de `pushManager` en `window`. Decide que envoltura arma el servidor |
| `verificado_at` | `timestamptz` | D-02. Cuando llego el aviso de prueba a ESTE dispositivo |
| `verificacion_grado` | `public.grado_verificacion_aviso` | §8.6 y §5.2 |
| `verificacion_token` | `uuid` | El token vivo del ultimo aviso de prueba enviado. Un solo uso |
| `verificacion_enviada_at` | `timestamptz` | Sin envio previo no hay nada que confirmar a mano |
| `verificacion_intentos` | `int not null default 0` | El tope de tres de §8.7, contado en la base |
| `visto_at` | `timestamptz` | Ultima vez que la app arranco con esta suscripcion. Alimenta el `title` del tooltip de §5.2 |

Mas `constraint push_subs_verificacion_shape check ((verificado_at is null) = (verificacion_grado is null))`
y `create unique index push_subs_verificacion_token_idx on public.push_subscriptions (verificacion_token) where verificacion_token is not null;`
(parcial, por la misma razon que `notifications_dedupe_idx`: sin el `where`, la semantica de los
NULL en un unico queda al azar del motor).

**(c) Los grants pasan de tabla a columna, y esto es el corazon del plan.**
La migracion 07 otorga `select, insert, update, delete` de tabla sobre `push_subscriptions` a
`authenticated`, con el comentario "la unica tabla que el aseador escribe libremente". Sigue siendo
cierto para lo que el navegador tiene que escribir, y deja de serlo para la evidencia. Escribir:

  - `revoke insert, update on public.push_subscriptions from authenticated;`
  - `grant insert (user_id, endpoint, p256dh, auth, user_agent, soporta_declarativo, visto_at) on public.push_subscriptions to authenticated;`
  - `grant update (endpoint, p256dh, auth, user_agent, soporta_declarativo, visto_at, revoked_at, revoked_reason) on public.push_subscriptions to authenticated;`
  - `select` y `delete` se quedan como estan.

El comentario tiene que decir por que, en una frase que el proximo lector no pueda malinterpretar:
el aseador tiene que poder registrar y reparar su propia suscripcion, pero **no puede firmar el acta
de que le llego**. Y anotar la restriccion de `CLAUDE.md`: los grants por columna no discriminan
usuarios (admin y aseador comparten el rol `authenticated`), y aqui eso esta bien, porque **ninguno
de los dos** debe escribir la evidencia.

`revoked_at` si queda escribible: que alguien marque muerta su propia suscripcion no hace dano.

**(d) `public.estado_avisos_aseadores()` — la unica superficie de D-03.**
Firma:

    returns table (
      aseador_id             uuid,
      suscripciones_vivas    int,
      verificado_por_toque   boolean,
      ultima_verificacion    timestamptz,
      ultimo_visto           timestamptz,
      ultimo_exito           timestamptz,
      primera_suscripcion_at timestamptz
    )

Cuerpo: guarda `if not private.is_admin() then raise exception ... using errcode = '42501'; end if;`
y despues un `left join` de `public.profiles` (rol aseador) contra `public.push_subscriptions`
filtrado por `revoked_at is null`, agrupado por perfil. Devuelve **una fila por aseador**, incluidos
los que tienen cero suscripciones: ese cero es justo el estado `Sin avisos` que D-03 existe para
hacer visible, y omitirlo obligaria a la UI a inventar la ausencia.

`verificado_por_toque` es `bool_or(s.verificacion_grado = 'toque')` con `coalesce(..., false)`: con
dos telefonos basta que uno este verificado de verdad.

**Ni `endpoint`, ni `p256dh`, ni `auth` aparecen en el `returns table`.** El comentario de la funcion
lo dice con la razon: el endpoint es una credencial portadora y el admin no necesita ninguna para
saber a quien llamar por telefono. Es la contrapartida de no anadir una policy de admin sobre la
tabla.

Par `revoke all ... from public, anon;` / `grant execute ... to authenticated;` pegado a la
definicion.

**(e) `public.registrar_prueba_de_aviso(p_endpoint text) returns uuid`.**
`select ... for update` sobre la suscripcion **propia** (`user_id = (select auth.uid())`) y no
revocada; si no aparece, `42501` (indistinguible "no existe" de "no es tuya": distinguirlos seria un
oraculo de enumeracion de endpoints ajenos). Si `verificacion_intentos >= 3`, `P0001` con `hint` en
espanol tomado literal de `05-UI-SPEC.md` §8.7. Si no, incrementa el contador, genera
`gen_random_uuid()` en `verificacion_token`, pone `verificacion_enviada_at = now()` y devuelve el
token.

El tope vive aqui y no en el navegador porque este camino **manda un push de verdad**: un boton que
dispara envios y se puede llamar en bucle es un amplificador. El contador de pantalla de §8.7 sigue
existiendo, pero es cortesia, no control.

**(f) `public.confirmar_prueba_por_toque(p_token uuid) returns void`.**
Busca la suscripcion propia cuyo `verificacion_token = p_token`; si no hay, sale sin hacer nada y
sin lanzar (el token ya se consumio, o es de otra sesion; lanzar aqui convertiria un reintento del
navegador en un error de pantalla). Si hay: `verificado_at = now()`, `verificacion_grado = 'toque'`,
`verificacion_token = null` (un solo uso), `verificacion_intentos = 0`.

**(g) `public.confirmar_prueba_a_mano(p_endpoint text) returns void`.**
Sobre la suscripcion propia: si `verificacion_enviada_at is null`, `P0001` (no se puede confirmar a
mano algo que nunca se mando). Si `verificacion_grado = 'toque'`, **no hace nada**: un grado bueno no
se degrada. En el resto de casos, `verificado_at = now()`, `verificacion_grado = 'manual'`,
`verificacion_token = null`.

Las tres funciones llevan su `comment on function` y su par revoke/grant. Ninguna usa
`current_date`. Ninguna toca `notifications`.
