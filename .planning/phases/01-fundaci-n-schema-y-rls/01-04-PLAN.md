1. **`tarifa_huesped bigint` y `pago_aseador bigint`**, no `numeric(12,2)`. Misma justificación del plan 03.
2. **Columnas de retención, que `ARCHITECTURE.md` no modela y CONTEXT.md exige en esta fase:**
   ```
   legal_hold        boolean not null default false,
   legal_hold_reason text,
   deleted_at        timestamptz,
   constraint cl_legal_hold_reason check (not legal_hold or legal_hold_reason is not null)
   ```
   más `create index cleanings_legal_hold_idx on public.cleanings (scheduled_date) where legal_hold;` para que la purga de la Fase 9 excluya barato. Los 7 `CHECK` de forma, verbatim de `ARCHITECTURE.md`: `cl_unmanaged_is_inert`, `cl_managed_has_state`, `cl_en_curso_shape`, `cl_completada_shape`, `cl_cancelada_shape`, `cl_pendiente_shape`, `cl_manual_types`. `cl_unmanaged_is_inert` es el que implementa la decisión de "gestión externa = misma tabla + discriminador `is_managed` snapshoteado + `state` anulable": fuerza NULL en estado, aseador, confirmación, huéspedes, instrucciones y las dos tarifas, y `is_urgent = false`. Sin él, "sin estado, sin aseador, fuera de métricas" sería convención de código, que es exactamente lo que la decisión quiere evitar.
   `cl_pendiente_shape` deja pasar `confirmado_at is not null` a propósito: "no puedo" devuelve el aseo a `pendiente` sin aseador **conservando** `confirmado_at`.

4. **Los dos índices únicos parciales, con `IS DISTINCT FROM` y nunca `<>`:**
   ```
   create unique index cleanings_one_active_per_property_date
     on public.cleanings (property_id, scheduled_date)
     where state is distinct from 'cancelada';

   create unique index cleanings_one_live_per_reservation
     on public.cleanings (reservation_id)
     where reservation_id is not null and state is distinct from 'cancelada';
   ```
   Cuatro hechos verificados sobre el primero: compila sobre el enum; un segundo aseo activo da `23505` con el nombre del índice en el mensaje; dos filas `cancelada` conviven; y **dos filas informativas con `state IS NULL` también chocan**, porque `NULL IS DISTINCT FROM 'cancelada'` es `TRUE` y la fila participa del índice — que es lo correcto, tampoco queremos dos filas informativas para el mismo apartamento y día.
   Esto **no se puede expresar como `CONSTRAINT`**: `alter table … add constraint c unique (…) where (…)` es error de sintaxis; solo `CREATE UNIQUE INDEX` admite predicado. Por eso el nombre que aparece en el error `23505` es el del índice, y por eso `lib/domain/errors.ts` discrimina por ese nombre.
   **Regla transversal:** toda consulta de "aseos vivos" en cualquier fase se escribe `state is distinct from 'cancelada'`. Se midió `Seq Scan` con `<>` incluso con `enable_seqscan = off`: el probador de implicación de predicados de Postgres no maneja `DistinctExpr`, así que una consulta con `<>` no puede usar el índice parcial. Para la unicidad da igual, para las consultas no.

5. Los índices operativos de `ARCHITECTURE.md`: `cleanings_agenda_idx`, `cleanings_aseador_idx`, `cleanings_unconfirmed_idx`, `cleanings_review_idx`. `cleanings_aseador_idx` es el que evita que la policy de RLS convierta cada lectura del aseador en un seq scan.

**No** habilitar RLS, ni policies, ni grants, ni el trigger de snapshot. RLS y grants van en el plan 07; el trigger, en el plan 06.
