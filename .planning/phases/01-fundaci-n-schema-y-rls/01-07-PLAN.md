El hecho verificado que justifica todo el archivo: sobre Supabase local, una tabla creada en `public` por el rol `postgres` sin tocar nada más muestra estos privilegios efectivos:

```
anon          | REFERENCES,TRIGGER,TRUNCATE
authenticated | REFERENCES,TRIGGER,TRUNCATE
postgres      | DELETE,INSERT,REFERENCES,SELECT,TRIGGER,TRUNCATE,UPDATE
service_role  | REFERENCES,TRIGGER,TRUNCATE
```

Tres consecuencias que se ejercieron una por una:
1. **Sin `grant select … to authenticated`, la RLS es irrelevante: el aseador no ve nada, y el error es `42501 permission denied`, no "0 filas".** Un dev que no lo sepa va a desactivar RLS o a meter `service_role` para "arreglarlo", que es exactamente el camino de fuga del código de acceso.
2. **`service_role` tiene `rolbypassrls = t` pero eso NO otorga privilegios de tabla.** Los workers de las Fases 3, 5 y 9 fallarían con `permission denied` si esta migración no los otorga.
3. **`anon` puede hacer `TRUNCATE`, y `TRUNCATE` ignora RLS por completo.** La explotabilidad práctica es baja (PostgREST no emite `TRUNCATE` y `anon` es `nologin`), pero revocarlo es gratis y elimina la clase entera de problema.

Además: el `revoke insert, update, delete on public.cleanings from authenticated` que propone `ARCHITECTURE.md` es un **no-op sobre privilegios que nunca existieron**. Se puede dejar escrito por claridad de intención, pero con un comentario que diga que no protege nada; lo que protege es no haber otorgado.

**Escribir el archivo siguiendo la matriz del bloque `<interfaces>`, tabla por tabla y con nombres explícitos**, nunca `grant select on all tables in schema public to authenticated`. La lista explícita es el artefacto que un revisor de seguridad audita; un `all tables` haría que cada tabla futura quede abierta por default.

Cerrar el archivo con:
```sql
grant all on all tables in schema public to service_role;
grant usage, select on all sequences in schema public to service_role;

revoke all on all tables in schema public from anon;
revoke all on all sequences in schema public from anon;

alter default privileges for role postgres in schema public revoke all on tables from anon;
alter default privileges for role postgres in schema public revoke all on sequences from anon;
```
El `alter default privileges` es lo que impide que las tablas creadas en las Fases 3 a 9 reintroduzcan el agujero de `anon`.

Dejar un comentario explícito encima del `grant all … to service_role`: **incluye `property_secrets`**, y es intencional — los workers y el admin necesitan escribir el código de acceso y la URL de iCal. Es precisamente por eso que el test de arquitectura que aísla `service_role` a `lib/supabase/admin.ts` (plan 01) no es opcional.

`grant usage on schema private to authenticated` va en la migración 08, no aquí, junto con la creación del esquema.

Un solo archivo, y está bien que sea largo: permite leer el modelo de autorización completo de arriba abajo. Es el archivo que un revisor de seguridad abre después del de grants.

**Parte A — esquema `private` y los 6 helpers.**
`create schema if not exists private; grant usage on schema private to authenticated;` El esquema **NO** se agrega a `[api] schemas` de `config.toml`: es lo que mantiene estas funciones fuera del alcance de PostgREST, y hace que `gen types --schema public` tampoco las emita.

Los 6 helpers, verbatim de `ARCHITECTURE.md`, cada uno `language sql stable security definer set search_path = ''` y con todos los nombres calificados por esquema. Dos ventanas distintas, a propósito:
- `my_property_ids()`: `hoy-1 .. hoy+7`. Es lo que el aseador necesita para planear.
- `my_unlockable_property_ids()`: `hoy .. hoy+1`. Es la ventana del código de acceso, mucho más estrecha.
Ambas usan `public.today_bog()`, **nunca** `current_date`: con `current_date` en la policy, el aseador pierde el código de la cerradura a las 19:00 de Bogotá porque la sesión corre en UTC.

`set search_path = ''` no es decorativo: sin él, el privilegio elevado de `SECURITY DEFINER` es un vector de escalada, y `db advisors` lo reporta como `function_search_path_mutable`.

`revoke all on function private.… from public, anon;` en cada helper, seguido de `grant execute … to authenticated`. En Postgres, `PUBLIC` tiene `EXECUTE` por defecto sobre toda función nueva (verificado: `proacl` NULL). Para `private` eso ya está cubierto porque `anon` no tiene `USAGE` sobre el esquema, pero escribirlo explícito es barato y evita depender de un detalle indirecto.

**Parte B — `enable row level security` en las 22 tablas de `public`.** Sin excepción, incluidas `property_secrets` y `storage_deletion_queue` que no tienen grants: el guardarraíl 1 de `02_guardarrailes.test.sql` no admite excepciones, y el punto ciego de `db advisors` es exactamente que no ve las tablas sin grant.

**Parte C — las policies.** El grafo debe ser un **DAG, sin ciclos**: si la policy de `properties` consulta `cleanings` y la de `cleanings` consulta `properties`, Postgres entra en recursión infinita de políticas (`42P17`), todo falla para todos los roles y aparece la presión de desactivar RLS. Aquí el DAG es `properties → cleanings` **vía función definer**, y `cleanings → nada`: la policy de `cleanings` es deliberadamente plana.

Patrón obligatorio en toda policy: `for … to authenticated` (nunca sin el `to`), y envolver toda llamada a función en `(select …)`. `(select private.is_admin())` y `(select auth.uid())` se evalúan como `InitPlan`, una vez por sentencia en vez de una vez por fila. Verificado indirectamente: `db advisors` **no** reporta `auth_rls_initplan` sobre las policies escritas así.

Las policies, por tabla, siguiendo la cobertura de `ARCHITECTURE.md` §Cobertura de policies por tabla y la matriz de grants del bloque `<interfaces>`:

- `cleanings`: `cleanings_admin_all` (`for all`, `using`/`with check` = `is_admin()`) y `cleanings_cleaner_select` (`for select`, `using ((select private.is_active_cleaner()) and aseador_id = (select auth.uid()))`). **Plana, sin referencia a `properties`.** Como no hay grant de DML, las ramas de escritura de la policy admin no son alcanzables desde `authenticated`; se dejan escritas para que el día que se otorgue un grant la policy ya esté.
- `properties`: `properties_admin_all` y `properties_cleaner_select` con `id in (select private.my_property_ids())`. Esta es la policy que impide la fuga por join: PostgREST resuelve `?select=*,properties(*)` como un join y es **la policy de `properties`** la que decide, no la de `cleanings`.
- `property_secrets`: **solo** `secrets_admin_all`. No hay policy de lectura para el aseador, ni la habrá. Su acceso pasa por RPC auditado.
- `profiles`: admin `for all`; aseador `for select` de su propia fila (`id = (select auth.uid())`).
- `room_types`, `checklist_tasks`, `missing_item_catalog`: admin `for all`; aseador `for select` sobre el catálogo global (para `missing_item_catalog`, globales `property_id is null` ∪ los de sus apartamentos vía `my_property_ids()`).
- `property_rooms`: admin `for all`; aseador `for select` con `property_id in (select private.my_property_ids())`.
- `cleaning_checklist_items`, `damages`, `expenses`, `missing_item_reports`: admin `for all`; aseador `for select` con `cleaning_id in (select private.my_cleaning_ids())`. Sin `INSERT`/`UPDATE` para el aseador: sus escrituras pasan por RPC.
- `missing_item_lines`: admin `for all`; aseador `for select` con `report_id in (select id from public.missing_item_reports where cleaning_id in (select private.my_cleaning_ids()))`.
- `cleaning_photos`: admin `for all`; aseador `for select` con `my_cleaning_ids()` y `for insert with check` con `my_writable_cleaning_ids()`. **Sin `UPDATE` ni `DELETE`**: la evidencia es inmutable, una foto subida no se reemplaza.
- `notifications`: `for select` y `for update` de las propias (`recipient_id = (select auth.uid())`), para admin y aseador por igual.
- `push_subscriptions`: `for all` de las propias (`user_id = (select auth.uid())`).
- `access_code_reads`, `app_settings`, `calendar_feeds`, `calendar_reservations`, `cleaning_state_transitions`: **solo** policy admin `for select` (o `for all` en `app_settings` y `calendar_feeds`, que el admin edita). Como el aseador tiene el grant pero ninguna policy que lo cubra, la RLS le filtra a 0 filas: el caso `is_empty`, no `throws_ok`.
- `storage_deletion_queue`: policy admin `for select`. No tiene grant, así que es inalcanzable desde `authenticated`; la policy existe para satisfacer el guardarraíl 2 ("toda tabla con RLS tiene al menos una policy"), porque RLS sin policy devuelve todo vacío **en silencio**, y ese silencio es lo que empuja a alguien a desactivar RLS.

**Parte D — vistas.** No crear vistas en esta fase (`v_cleaning_margin`, `v_carga_diaria` y `v_admin_alerts` son de las Fases 4 y 7). Si el ejecutor crea alguna, **debe** llevar `with (security_invoker = on)`: sin él, la vista corre con los privilegios del owner y salta la RLS de las tablas base. Medido: 4 filas en vez de 1. `db advisors` lo cataloga como ERROR `security_definer_view` y el guardarraíl 3 lo verifica.

**Deuda aceptada y registrada:** este diseño emite 3 `WARN multiple_permissive_policies` sobre `cleanings`, `profiles` y `properties`, porque "una policy para admin + una policy para aseador, mismo rol, misma acción" es exactamente lo que ese lint detecta. Consolidarlas en un `OR` haría el modelo de autorización mucho menos legible por una ganancia de rendimiento irrelevante a 39 unidades. Por eso CI usa `--fail-on error` y no `--fail-on warn`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| cliente (JWT de aseador) → PostgREST → `public.*` | El aseador consulta la API directamente; nada intermedia salvo grants y RLS |
| cliente (JWT de admin) → PostgREST → `public.*` | Mismo rol Postgres que el aseador: solo RLS los distingue |
| `anon` (sin sesión) → `public.*` | Superficie con la publishable key, que es pública por diseño |
| `service_role` (worker) → `public.*` | `BYPASSRLS`: ninguna policy lo frena |
