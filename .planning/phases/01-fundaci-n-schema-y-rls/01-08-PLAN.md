Crear con `npx supabase migration new 09_rpc`. Regla uniforme para las 6 funciones de este archivo: `language plpgsql security definer set search_path = ''`, todos los nombres calificados por esquema, y al final del archivo, por cada función:

```sql
revoke all on function public.<fn>(<args>) from public, anon;
grant execute on function public.<fn>(<args>) to authenticated;
```

Ese `revoke` **es obligatorio, no decorativo**: en Postgres, `PUBLIC` tiene `EXECUTE` por defecto sobre toda función nueva (verificado con `proacl` NULL, y `anon` pudo llamar a `public.today_bog()`). Sin él, `anon` puede invocar cualquier RPC de `public`.

**`reveal_access_code(p_cleaning uuid)`.** Patrón verificado, en este orden exacto:
1. `select c.property_id into v_prop from public.cleanings c where c.id = p_cleaning and c.aseador_id = (select auth.uid()) and c.is_managed and c.state in ('pendiente','en_curso') and c.scheduled_date between public.today_bog() and public.today_bog() + 1;`
2. `if v_prop is null then raise exception 'no_autorizado' using errcode = '42501'; end if;`
3. `insert into public.access_code_reads (property_id, cleaning_id, read_by) values (v_prop, p_cleaning, (select auth.uid()));`
4. `return query select s.codigo_acceso, s.tipo_cerradura, s.notas_acceso from public.property_secrets s where s.property_id = v_prop;`

Que la auditoría vaya **antes** del `return query` y en la misma función garantiza que no existe lectura sin rastro: si el `return` falla, la transacción se revierte entera; si tiene éxito, la fila de auditoría ya está escrita. Este es el dato más sensible del sistema — abre físicamente un apartamento con huéspedes y pertenencias adentro, y el 90% de las unidades tiene cerradura inteligente.

Tres cosas que este patrón da y una policy de `SELECT` no daría: ventana temporal estrecha (hoy y mañana, `today_bog()` y nunca `current_date`), rastro de auditoría, y un solo punto donde endurecer la regla.

`p_cleaning` es un uuid, no un `property_id`: obliga a que la autorización se ancle a un aseo concreto asignado, no a "tener algún trabajo en ese apartamento". Es lo que hace que un aseo a 5 días **no** revele el código aunque el apartamento sí sea visible por la ventana `-1..+7` de `my_property_ids()`.

**`confirm_cleaning(p_cleaning uuid, p_num_huespedes smallint, p_instrucciones text)`.**
1. Verificar `(select private.is_admin())`; si no, `raise exception 'no_autorizado' using errcode = '42501'`.
2. `select … into … from public.cleanings c join public.properties p on p.id = c.property_id where c.id = p_cleaning and c.is_managed and c.state = 'pendiente' and c.confirmado_at is null for update;` Si no hay fila, `'P0001'` con mensaje `'aseo_no_confirmable'`.
3. Si `p.responsable_id is null`, `'P0001'` con `'sin_responsable'`. Es el hueco conocido del modelo: una unidad gestionada por una empresa externa sin usuario en el sistema no tiene a quién asignarse. Falla explícito en vez de dejar el aseo asignado a NULL en silencio.
4. `update public.cleanings set aseador_id = p.responsable_id, num_huespedes = p_num_huespedes, instrucciones = p_instrucciones, confirmado_at = now(), confirmado_by = (select auth.uid()) where id = p_cleaning;`
5. **Materializar el checklist** insertando en `public.cleaning_checklist_items` el producto de `property_rooms` activos del apartamento por sus `checklist_tasks` activas del tipo de cuarto, copiando `room_label = pr.etiqueta`, `task_label = ct.descripcion` y `requiere_foto = ct.requiere_foto` como **snapshot**. `on conflict (cleaning_id, property_room_id, checklist_task_id) do nothing`.
   Se materializa al confirmar y no al crear el aseo porque un aseo sin confirmar puede ser cancelado por el sync, y los cuartos del apartamento pueden editarse entre la detección y la confirmación. Y se copia como snapshot porque la biblioteca global de tareas puede cambiar y un checklist ya generado no debe reescribirse.
6. `insert into public.notifications (recipient_id, type, title, body, cleaning_id, property_id, dedupe_key)` con `type = 'asignacion'` para el responsable. Es la costura conocida y documentada del ROADMAP: al confirmar, el aseo queda asignado pero **no se notifica a nadie** hasta que exista el worker de la Fase 5. El evento se escribe en el outbox y se drena después. Es intencional, no un olvido; dejarlo escrito como comentario en la función.

Ojo con el `state`: `confirm_cleaning` **no** cambia el estado. El aseo sigue en `pendiente`, ahora confirmado y asignado. La transición a `en_curso` la hace `start_cleaning`. `cl_pendiente_shape` permite `confirmado_at is not null` con `state = 'pendiente'` justamente por esto.

**`start_cleaning(p_cleaning uuid)`.** `perform 1 from public.cleanings c where c.id = p_cleaning and c.aseador_id = (select auth.uid()) and c.is_managed and c.state = 'pendiente' and c.confirmado_at is not null for update;` Si `not found`, `'42501'`. Luego `update … set state = 'en_curso', started_at = now()`. El `cl_en_curso_shape` exige `confirmado_at`, `aseador_id` y `started_at` no nulos y `finished_at` nulo, así que el `CHECK` y el RPC se refuerzan mutuamente.

**`finish_cleaning(p_cleaning uuid)`.** Verbatim del research, que lo verificó ejecutando: el `perform … for update` con `state = 'en_curso'`, el `42501` si no hay fila, y el guard agregado:
```sql
if exists (
  select 1 from public.cleaning_checklist_items i
  where i.cleaning_id = p_cleaning
    and ( i.done_at is null
       or ( i.requiere_foto and not exists (
              select 1 from public.cleaning_photos ph
               where ph.checklist_item_id = i.id)))
) then
  raise exception 'checklist_incompleto' using errcode = 'P0001';
end if;
```
Este guard **es** PWA-07 ("Terminé queda bloqueado mientras falte una tarea o la foto de algún cuarto") impuesto en la base. Un `GRANT UPDATE (state, finished_at)` no podría expresarlo: el invariante es multi-fila.
Al final, `update … set state = 'completada', finished_at = now()`, más un `insert into public.notifications` con `type = 'aseo_completado'` para los admins.

**`decline_cleaning(p_cleaning uuid, p_motivo text)`.** El caso que justifica el patrón RPC entero, porque son tres efectos que tienen que ocurrir **atómicamente**:
1. `update public.cleanings set state = 'pendiente', aseador_id = null, started_at = null where id = p_cleaning and aseador_id = (select auth.uid()) and state in ('pendiente','en_curso');` — vuelve a pendiente **sin aseador**, y **conservando `confirmado_at`**: el admin ya puso número de huéspedes e instrucciones, ese trabajo no se pierde.
2. `insert into public.notifications (…) values (…, 'no_puedo', …)` para los admins, con `p_motivo` en el `body` y en `payload`.
3. La transición `en_curso -> pendiente` queda registrada sola por el trigger `AFTER UPDATE OF state` (plan 06). No insertar a mano en `cleaning_state_transitions`.
Si el `update` no afecta ninguna fila, `'42501'`.

**`toggle_checklist_item(p_item uuid, p_done boolean, p_nota text)`.** Verifica que el item pertenezca a un aseo del caller en estado `en_curso` (`i.cleaning_id in (select private.my_writable_cleaning_ids())`); si no, `'42501'`. Luego `update public.cleaning_checklist_items set done_at = case when p_done then now() else null end, done_by = case when p_done then (select auth.uid()) else null end, nota = p_nota where id = p_item;`
Existe en esta fase porque sin ella `finish_cleaning` no tiene forma de llegar a su condición de salida desde el cliente, y añadirla en la Fase 6 obligaría a repensar los grants de `cleaning_checklist_items`, que ya quedaron cerrados en `select` a secas.

**Explícitamente fuera de alcance de esta fase, y por qué:** `report_damage()`, `report_expense()` y `report_missing_items()` van a la **Fase 6**. Sus requisitos (REPORT-01, REPORT-02, REPORT-03) están mapeados a esa fase en `REQUIREMENTS.md`, y su forma depende del payload de notificación y del flujo de subida de foto que se definen ahí. Dejar esto escrito como comentario al final del archivo para que en la Fase 6 nadie lo redescubra.

`cancel_cleaning()` y `reschedule_cleaning()` van a la **Fase 4** (ASEO-06, ASEO-08, ASEO-09) por la misma razón.


**Las tres policies** de `ARCHITECTURE.md`, verbatim:
- `evidencia_admin_all`: `for all to authenticated`, `using`/`with check` = `bucket_id = 'evidencia' and (select private.is_admin())`.
- `evidencia_cleaner_insert`: `for insert to authenticated with check (bucket_id = 'evidencia' and (select private.is_active_cleaner()) and (storage.foldername(name))[1] in (select id::text from private.my_writable_cleaning_ids() as id))`.
- `evidencia_cleaner_select`: `for select to authenticated using (… and (storage.foldername(name))[1] in (select id::text from private.my_cleaning_ids() as id))`.
- **Sin `UPDATE` ni `DELETE` para el aseador.** La evidencia es inmutable: una foto subida no se puede reemplazar.

Dos detalles que no son estilo:
- La comparación se hace **como `text`**, con `id::text`, y no casteando el segmento del path a `uuid`. Un path malformado debe producir un deny limpio, no un error de tipo dentro de la policy.
- La ventana de escritura (`my_writable_cleaning_ids()`, solo `state = 'en_curso'`) es más estrecha que la de lectura (`my_cleaning_ids()`, que incluye histórico corto). Son dos funciones distintas a propósito.

**Advertencia honesta que hay que dejar como comentario en la migración:** esto funciona en local (verificado: `supabase db reset` deja las policies presentes en `pg_policies`), pero `postgres` **no** es miembro de `supabase_storage_admin` ni superusuario, así que funciona por un permiso que Supabase concede de forma no evidente en el grafo de roles. **En el proyecto hosted hay que confirmarlo**, y esa confirmación es la tarea con checkpoint humano del plan 09. Marcar el bloque con `-- [ASSUMED en hosted — verificar en el primer db push a dev, ver plan 01-09]`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| cliente (JWT de aseador) → RPC `SECURITY DEFINER` | La función corre como `postgres` y salta RLS: su propio guard es la única autorización |
| navegador del aseador → `storage.objects` | Sube directo desde el móvil con su JWT; la policy autoriza por el primer segmento de la ruta |
| `anon` → RPC de `public` | `PUBLIC` tiene `EXECUTE` por default sobre toda función nueva |
