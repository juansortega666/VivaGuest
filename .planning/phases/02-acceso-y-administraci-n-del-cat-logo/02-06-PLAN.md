Crear los cuatro archivos siguiendo el código de referencia del research §Patrón 1. Ninguna fábrica a nivel de módulo: un `export const supabase = createServerClient(...)` de nivel superior se comparte entre peticiones concurrentes con las cookies del primero que lo instanció, y en Fluid Compute de Vercel eso es fuga cruzada de sesión.

**`lib/supabase/middleware.ts` es el archivo crítico.** El callback `setAll` recibe **dos** argumentos: `(cookiesToSet, headers)`. El segundo trae `Cache-Control: private, no-cache, no-store, must-revalidate, max-age=0`, `Expires: 0` y `Pragma: no-cache`, y hay que aplicarlos al `supabaseResponse`. **El ejemplo oficial de Supabase todavía escribe la firma de un solo argumento y compila sin un solo error de TypeScript**, porque TS permite implementar un tipo de función con menos parámetros de los declarados. No hay ninguna señal. Copiar el código de §Patrón 1, no el de la web.

Entre `createServerClient` y `await supabase.auth.getUser()` **no puede haber nada**. Un `await` de por medio y las cookies se escriben tarde: el usuario se desloguea solo cada cierto rato.

`getUser()`, **nunca `getSession()` ni `getClaims()`**. Medido: tras banear a un usuario con el mismo access token sin expirar, `getUser()` devuelve 403 `user_banned` y `getClaims()` responde OK. La documentación oficial de Supabase recomienda `getClaims()` hoy, y para el criterio 4 del ROADMAP es la respuesta equivocada. Dejar ese párrafo como comentario en el archivo, con la medición, para que nadie lo "modernice".

`middleware.ts` lee el rol de **`user.app_metadata.role`**. Medido: un aseador **sí puede** poner `user_metadata.role = 'admin'` con `supabase.auth.updateUser()` y verlo en el JWT siguiente. No gana nada —la RLS lee `profiles.role` vía `private.is_admin()`— pero rutearlo al shell del admin le daría una pantalla llena de errores `42501`. Llama a `resolverRedireccion` del plan 02-02. Si hay que redirigir, se crea el `NextResponse.redirect` y **se le copian todas las cookies del `supabaseResponse`**: saltarse ese copiado es la causa clásica de "los usuarios se deslogean solos". Si no, se devuelve el `supabaseResponse` **tal cual**, sin reconstruirlo.

El `matcher` es el del research §1.4, con `api/cron`, `sw.js` y `manifest.webmanifest` ya excluidos. Se excluyen ahora para las Fases 3, 5 y 6: es gratis y evita una edición cruzada después.

`lib/auth/guards.ts` con `NoAutorizado`, `exigirSesion()` y `exigirAdmin()`. Comentario obligatorio: esto es **defensa en profundidad, NO la frontera**. La frontera es la RLS. Aunque el guard se cayera, un aseador que invoque la action recibiría 0 filas o `42501`. El guard existe para fallar temprano con un mensaje en español y para no filtrar la existencia de recursos por el código de error de Postgres. Un Server Action es un endpoint HTTP público: que el botón solo se renderice en `(admin)` no autoriza nada.

`lib/auth/guards.test.ts` prueba los 5 casos del bloque `behavior` con el cliente de Supabase stubbeado. Vive bajo `lib/` para que `vitest.config.ts` lo recoja.

`lib/domain/acciones.ts` con el tipo `ResultadoAccion`. Es el contrato de retorno de todas las Server Actions de la fase: si trae `campo`, el error va inline bajo ese campo; si no, va a toast y el formulario conserva todo lo escrito.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Navegador → middleware | Cookies de sesión que el CDN podría cachear |
| JWT → decisión de ruteo | Claims que el propio usuario puede escribir en parte |
| Navegador → Server Action de login | Endpoint HTTP público que acepta credenciales |
| Middleware → autorización | El middleware **no** es la frontera |
