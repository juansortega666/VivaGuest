<objective>
Baja y reactivación de cuentas de aseador, con revocación de acceso inmediata y verificable.

Propósito: es el criterio 4 del ROADMAP —"el aseador desactivado pierde el acceso de inmediato aunque tuviera la sesión abierta"— y contiene **la corrección más importante de todo el research**. `auth.admin.signOut(id, 'global')`, que documentan `research/ARCHITECTURE.md` y `02-CONTEXT.md`, **no existe con esa firma**: la real es `signOut(jwt, scope)` y exige el JWT del usuario, que el admin no tiene. Lo que sí revoca, medido de punta a punta, es `profiles.is_active = false` más `updateUserById(uid, { ban_duration })`. Y hay un corolario que se olvida: **reactivar exige las dos operaciones también**; hacer solo la primera deja al aseador marcado `Activo` en la lista y sin poder entrar.

Salida: una sola función de dominio con un `activo: boolean` que hace siempre las dos mitades, el diálogo con consecuencias calculadas, y el test de integración que es la prueba central de PLAT-04.
</objective>

Añadir a `app/(admin)/aseadores/_actions.ts` la función `fijarActivacionAseador(uid, activo)`.

**Es una sola función con un booleano, y esa es la decisión de diseño.** Escribir `desactivarAseador` y `reactivarAseador` por separado es exactamente cómo alguien implementa una de las dos mitades y no la otra. Con una sola función, olvidarse de una mitad es imposible.

Empieza, como todas las actions de la fase: `exigirAdmin()`, después validación del `uid`, después `createAdminClient()`.

Las dos operaciones, **siempre las dos, en este orden al desactivar**:
1. `update profiles set is_active = <activo>, deactivated_at = <activo ? null : now()>`. Las dos columnas **juntas**: el CHECK `profiles_deactivation_coherent` exige `is_active = (deactivated_at is null)`, así que un `update profiles set is_active = false` a secas revienta con 23514. Esta es la capa que de verdad revoca datos: `private.is_active_cleaner()` devuelve `false` y **toda** policy del aseador deja de casar, así que da 0 filas en cualquier consulta aunque el token siga vivo, y lo hace en la siguiente sentencia SQL.
2. `admin.auth.admin.updateUserById(uid, { ban_duration: activo ? 'none' : '876000h' })`. Esta capa es la que hace que el aseador **vea** que perdió el acceso: `getUser()` del middleware pasa a 403 `user_banned` y la siguiente navegación lo manda a `/login`.

**Ninguna de las dos sobra.** Sin la primera, un token vivo seguiría leyendo datos hasta 30 minutos. Sin la segunda, el aseador se queda mirando una pantalla vacía sin entender por qué. Dejar esa tabla como comentario en la función.

**No llamar a `auth.admin.signOut`.** La firma real es `signOut(jwt, scope)` y hace un POST con el JWT del usuario como bearer; el admin no tiene ese JWT. Y probado: llamándolo con el JWT del propio aseador **después** de banearlo devuelve `403 User is banned`. Dejar un comentario que diga que esa API no existe con la firma que documentan `research/ARCHITECTURE.md` y `02-CONTEXT.md`, para que nadie la reintroduzca leyendo esos documentos.

Si la segunda operación falla después de que la primera tuvo éxito, devolver un `ResultadoAccion` en error que lo diga sin filtrar detalles internos, y **no** revertir la primera: el estado seguro es "sin acceso a datos", no "acceso restaurado".

Añadir también `consecuenciasDeBaja(uid)`: tres `count` sobre `properties` con el cliente del **usuario**, no con el de servicio — `properties` es legible por el admin con su propio JWT (39 filas, medido) y no hace falta saltar la RLS para contar. Devuelve responsable de cuántos, suplente en cuántos, y de cuántos **activos** es responsable. El tercero es el que decide si el diálogo muestra su bloque ámbar.

`lib/auth/revocacion.integration.test.ts` es el archivo más importante de esta fase. Cinco aserciones, todas contra el stack local con JWT reales, cada una correspondiendo a algo que el research **midió**:

1. **Token vivo + desactivación ⇒ 0 filas.** El aseador hace login de verdad, se guarda su `access_token`, se le pone `is_active = false`, y **con el mismo token** se consulta `properties`. `data.length === 0`. Es la aserción central de PLAT-04: demuestra que la revocación de datos es inmediata y no espera a que el token expire.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Empleado que sale → sus datos | Un token ya emitido verifica hasta expirar |
| Server Action de baja → GoTrue Admin API | Puede banear a cualquier usuario |
| Estado de la UI → estado real de acceso | La lista puede mentir si solo se hace media operación |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-41 | Elevation of Privilege | Aseador dado de baja que conserva el acceso | mitigate | Doble capa medida: `profiles.is_active = false` corta los datos en la siguiente sentencia SQL vía `private.is_active_cleaner()`, y `ban_duration` corta la sesión en la siguiente navegación vía `getUser()`. Las dos en una sola función. Test de integración con el token guardado antes de la baja |
| T-02-42 | Spoofing | Reactivación a medias que aparenta acceso restaurado | mitigate | `fijarActivacionAseador(uid, true)` hace `is_active = true`, `deactivated_at = null` **y** `ban_duration: 'none'`. Test que prueba las dos mitades por separado, porque hacer solo la primera deja `user_banned` |
| T-02-43 | Tampering | CHECK `profiles_deactivation_coherent` disparado | mitigate | `is_active` y `deactivated_at` se escriben siempre juntos. Un update de una sola columna revienta con 23514, que `mapDbError` traduce a `Estado de activación incoherente.` — mensaje de bug interno que no debería verse nunca |
| T-02-44 | Elevation of Privilege | `fijarActivacionAseador` invocada por un aseador | mitigate | `exigirAdmin()` primero. Y aunque fallara, la RLS de `profiles` no deja a un aseador escribir la fila de otro |
| T-02-45 | Repudiation | Baja sin rastro | mitigate | `profiles.deactivated_at` registra cuándo. **Sin "Deshacer"** en el toast: esconder la reactivación tras un undo falsearía el registro. Es decisión del contrato, no comodidad |
| T-02-46 | Denial of Service | Admin que se desactiva a sí mismo | accept | El menú solo se renderiza en filas con `role = 'aseador'`, así que la lista de aseadores no incluye admins. No se construye una guarda adicional en el servidor: con dos personas y un solo admin, el escenario requiere invocar la action a mano contra el propio uid |
| T-02-47 | Spoofing | Fijación de sesión tras la reactivación | mitigate | El ban invalida las sesiones anteriores; al levantarlo, el usuario tiene que autenticarse de nuevo. Medido: el re-signIn falla mientras el ban está puesto |
</threat_model>
