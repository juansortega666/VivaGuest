<objective>
La capa de datos del catálogo de apartamentos: lecturas tipadas para los RSC y las Server Actions de escritura, con los secretos por la única ruta que la base permite.

Propósito: separar las acciones de la pantalla que las consume. El formulario del plan 02-12 es la pieza más grande de la fase y no debería además estar descubriendo con qué cliente se escribe cada tabla. Aquí se fija eso, con un hallazgo medido que sorprende: **`property_secrets` devuelve `42501` incluso para un admin con su propio JWT**. Existe una policy `secrets_admin_all` que sugiere lo contrario, pero la migración 07 nunca otorgó privilegios de tabla sobre esa tabla a `authenticated`. Un executor que lea las policies y no los grants va a escribir la action con el cliente equivocado y a perder una hora.

Salida: `lib/data/apartamentos.ts`, `app/(admin)/apartamentos/_actions.ts` y el test de integración que fija las dos fronteras.
</objective>

`app/(admin)/apartamentos/_actions.ts` con `'use server'` e `import 'server-only'`.

**Cada action arranca igual: `exigirAdmin()`, después Zod, después —solo si hace falta— `createAdminClient()`.** Un Server Action es un endpoint HTTP público; que el botón se renderice en `(admin)` no autoriza nada.

`guardarApartamento(entrada)`: recibe los campos del formulario más un modo, `'borrador'` o `'activar'`. Valida con `esquemaBorrador` o `esquemaActivar` según el modo — el esquema de activación es más estricto que la base a propósito y esa divergencia está documentada en el plan 02-03.

Reparto de clientes, medido y no negociable:
- **`properties`** se escribe con el **cliente del usuario** (`createClient()` de `lib/supabase/server.ts`). El admin tiene grant y policy: medido, 39 filas y upsert OK.
- **`property_secrets`** (`codigo_acceso`, `tipo_cerradura`, `notas_acceso`, `ical_url`) se escribe **y se lee** con `createAdminClient()`. Medido: `42501 permission denied for table property_secrets` en SELECT y en UPSERT, **incluso siendo admin con JWT de usuario**. La policy `secrets_admin_all` existe y es inalcanzable porque la migración 07 nunca otorgó privilegios de tabla; es deliberado (`-- Sin ningun grant -> property_secrets, storage_deletion_queue`) pero la policy hace parecer lo contrario. **No hay otra ruta.** Dejar ese párrafo como comentario, con la medición, porque es exactamente el punto donde alguien pierde una hora.
- **`calendar_feeds`** sí es escribible con el JWT del admin (medido). Lo usa el plan 02-14.

`activarApartamento(id)` y `desactivarApartamento(id)`: update de `is_active` sobre `properties` con el cliente del usuario. Al activar, revalidar la regla con `esquemaActivar` sobre la fila leída **antes** de intentar el update: los tres CHECK de activación no deben poder dispararse desde la UI, y el §8.2 del UI-SPEC es la red que lo impide.

Errores: **todo** pasa por `mapDbError`. Nunca se renderiza un string crudo de Postgres. Si `campoDeConstraint` reconoce el constraint, devolver `{ ok:false, error, campo }` para que el formulario lo pinte inline; si no, sin `campo`, y va a toast.

`leerSecretos(id)`: `exigirAdmin()` y después `createAdminClient()`. Devuelve los cuatro campos. **Este es un endpoint público que devuelve el código de acceso de un apartamento**, así que el guard no es opcional: es lo único que separa esa función de una fuga. Comentario explícito.

**No crear ninguna función en `public`.** Todo el CRUD va por PostgREST con RLS y `property_secrets` por el cliente de servicio. Si algún día hiciera falta un RPC para escribir los secretos de forma atómica, necesitaría `revoke all on function public.<f>(<args>) from public, anon` y `grant execute … to authenticated` pegados a la definición, porque `alter default privileges` no puede quitarle `EXECUTE` a PUBLIC en PG 17.6 (hallazgo 5 de `deferred-items.md`, medido dos veces). Y merecería una aserción pgTAP propia. Dejarlo escrito.

**Al comentar sobre la clave de servicio, no escribir su nombre literal**: el guardarraíl 1 hace grep de ese token.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Navegador → Server Actions del catálogo | Cuatro endpoints HTTP públicos que escriben el catálogo |
| Server Action → `property_secrets` | El código de acceso y la URL iCal son credenciales |
| Cliente de usuario → RLS | La frontera real de autorización |
| Respuesta de `leerSecretos` → DOM | Un secreto que llega al navegador puede quedar en una captura |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-48 | Elevation of Privilege | Actions del catálogo invocadas por un aseador | mitigate | `exigirAdmin()` primero en las cuatro. Y la frontera real: `properties_admin_all` deja el update en 0 filas para un aseador (medido) |
| T-02-49 | Information Disclosure | `codigo_acceso` alcanzable por un aseador | mitigate | Vive en `property_secrets`, **sin grant para `authenticated`**. No hay policy que pueda filtrarlo por error ni embed de PostgREST que lo alcance: es imposible por construcción. La única ruta legítima del aseador es el RPC `reveal_access_code()` de la Fase 1, con ventana y auditoría |
| T-02-50 | Information Disclosure | `leerSecretos` como endpoint público | mitigate | Guard de admin como primera sentencia. Devuelve secretos de un solo apartamento por llamada. El plan 02-12 lo consume solo desde el formulario de edición del admin |
| T-02-51 | Information Disclosure | `ical_url` en un log o en un mensaje de error | mitigate | Regla dura: la URL nunca se escribe en un log ni en `last_error`. En este plan `_actions.ts` no la registra en ningún sitio; el plan 02-14 la maneja con la misma regla |

| T-02-55 | Tampering | Cluster nuevo creado por un typo | accept | `properties.cluster` es `text not null`, ni enum ni tabla, por decisión de la Fase 1. Mitigado con `trim` y sugerencia de coincidencias en el combobox del plan 02-12. Un cluster de más es ruido, no un fallo de seguridad |
